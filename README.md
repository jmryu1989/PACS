# HALO PACS 개발 안내

Orthanc, NestJS/Prisma, PostgreSQL, Keycloak, nginx로 구성된 의료영상 시스템이다.
업무 화면은 `worklist-v0/hpacs-lite/main.html`의 바닐라 JavaScript이며, 영상 표시는 고정 OHIF 구성을 사용한다.

## 작업을 시작하기 전에

개발 규칙은 [AGENTS.md](AGENTS.md), 시험 실행과 제한은 [tests/README.md](tests/README.md)를 따른다. 인접한 비공개 `docs-repo`가 있으면 그 `README.md`가 안내하는 현행 상태·로드맵·평가 기준을 먼저 읽는다. 없으면 대화에서 제공된 범위를 따르고, 오래된 단계 번호로 다음 작업을 추정하지 않는다.

기존 작업 파일, DB, DICOM 원본, 계정과 설정을 보존한다. 작업 전에 Git 상태와 실행 중인 컨테이너를 확인하며, 문서 정리를 이유로 환경을 다시 만들지 않는다.

## 로컬 개발 환경

Docker Desktop과 Docker Compose가 필요하다. Python 기반 시험의 준비물은 [시험 안내](tests/README.md)를 따른다.

새 환경에서만 `.env.example`을 로컬 `.env`로 복사하고 필요한 자격증명을 직접 설정한다. 기존 `.env`를 덮어쓰지 않으며 비밀번호·토큰·키를 저장소에 넣지 않는다.

기동이 필요하면 저장소 루트에서 실행한다. 이미 실행 중인 환경은 변경에 필요한 서비스만 갱신한다.

```sh
docker compose up -d --build
docker compose ps
```

기본 정식 입구는 **[https://localhost:9443/](https://localhost:9443/)** 이다. 로컬 인증서와 게시 포트 설정을 확인한 뒤 접속한다. `PUBLIC_ORIGIN`이나 `PUBLIC_PORT`를 변경한 환경에서는 그 환경의 정식 주소를 사용한다.

| 경로 | 용도 |
|---|---|
| `/` | 로그인 화면으로 이동한 뒤 판독 업무 시작 |
| `/ohif/` | 영상 뷰어 |
| `/api/health` | API 상태 확인 |
| `/auth/` | Keycloak 인증 경로 |

`/api`, `/auth`, `/worklist`, `/ohif`, `/dicom-web`은 같은 출처를 사용한다. 8042·3000·8080 같은 서비스 포트는 디버깅용이며 일반 사용자의 접속 주소로 안내하지 않는다. 컨테이너의 `Up` 표시와 함께 정식 HTTPS의 API 상태 및 실제 로그인을 확인한다.

사람 계정은 가입 신청 또는 관리자 발급으로 준비하며, 사용 전에 이메일 검증·관리자 승인과 기관·역할 배정을 확인한다. 브라우저 인증은 BFF의 HttpOnly 세션과 OIDC Authorization Code + PKCE를 사용한다. Gateway 서비스 계정은 사람 계정과 분리하고 자기 기관의 허용된 수신 경로에만 사용한다. 설정은 [Keycloak 안내](keycloak/README.md)와 [Gateway 안내](gateway/README.md)를 참고한다.

## 판독과 영상 접근

판독 상태·초안·기관 접근 규칙은 [개발 규칙 §1](AGENTS.md#1-판독권한-불변조건), API 구조는 [PACS concern 지도](api/src/pacs/README.md)를 따른다.

### 3D Cursor(대응점 표시)

같은 검사·같은 원본 환자·같은 FrameOfReferenceUID의 고전 CT/MR stack 화면에서만 동작하는 명시적 지정 모드다.
`worklist-v0/hpacs-lite/three-d-cursor-model.js`가 좌표를, `viewer-three-d-cursor.js`가 화면 제어를 맡는다.

- 유효한 IOP/IPP/PixelSpacing·직교 단위 평면·같은 방향·겹치지 않는 slice 위치를 모두 확인한 화면만 대상으로 삼는다. slice 간격은 고르지 않아도 된다(장 하나가 빠졌거나 끝 장만 떨어진 시리즈): 실제로 있는 장 가운데 가장 가까운 장을 쓰고, 빠진 자리에 떨어진 점이 어느 장에서도 평면 거리 한도 밖이면 그 사유로 거절한다. 촬영 범위는 처음·끝 장에서 각 끝의 인접 간격 절반까지다. 순서가 섞인 시리즈도 전체 평면 거리를 비교해 고르며, 두 장이 같은 거리면 slice 법선 방향 위치(projection)가 작은 장을 고른다(입력 순서와 무관). 영상 밖·촬영 범위 밖·식별이나 형상이 섞인 경우에는 좌표를 추정하지 않고 사유와 함께 거절한다.
- 클릭 좌표는 고정 OHIF와 같은 방식(cornerstone 표시 요소의 `getBoundingClientRect()` 기준)으로 계산한다. 영역 안의 자식 요소를 눌러도 같은 점을 가리키며, 표시 영역을 확인할 수 없으면 계산하지 않고 거절한다. 표식도 **같은 표시 요소**에 붙여 그리므로, 표시 요소가 바깥 칸 안쪽에 들어 있어도 클릭한 점과 그려진 점의 기준이 어긋나지 않는다. 보이는 영역 밖의 점은 잘라내어 옆 화면에 그리지 않는다. 고정 렌더러는 canvas 좌표를 자신의 그리기 버퍼 단위로 읽고 돌려준다(GPU 경로는 버퍼 화소÷DPR, CPU 경로는 버퍼 화소 그대로). 버퍼는 정수 화소이고 canvas 상자는 배치가 정한 크기라서 둘이 다르므로, 렌더러와 주고받는 좌표는 버퍼 단위로 바꿔 넘기고 돌려받는다(렌더러 자신의 `cornerstone-canvas`가 표시 요소의 모서리에서 시작할 때). 이 환산은 버퍼가 렌더러가 지금 DPR에서 만드는 크기(client 크기×단위의 내림, 또는 상자×단위의 내림·올림)이고 GPU 경로에서 복사해 오는 영역이 그 버퍼와 같을 때에만 렌더러의 것이다. 그 전제가 깨진 화면 — 창 크기는 그대로인데 DPR만 바뀐 경우(배율이 다른 모니터로 옮김: 고정 렌더러가 옛 버퍼를 그대로 둔다)와 resize가 끝나기 전 — 은 좌표를 계산하지 않고 "영상 표시 요소를 확인하지 못했습니다."로 거절하며, 그 화면에 남아 있던 표식도 지운다. 렌더러가 버퍼를 다시 잡으면(다음 resize) 다시 동작한다.
- 화면 배치는 건드리지 않는다. 호스트 스타일시트가 이미 위치를 지정한 요소에는 쓰지 않고, 이 기능이 직접 넣은 인라인 값만 종료할 때 되돌린다. 한 요소에 두 화면이 연결되어 구분할 수 없으면 두 화면 모두 사용하지 않는다.
- 대상 화면 이동은 하나씩 await하고, 실제로 그려진 영상(`getCornerstoneImage().imageId`)이 기대한 SOP와 같을 때만 표식을 남긴다. 화면의 stack이 교체되면 그 뒤로 이동 요청을 보내지 않는다. 이동을 요청한 직후(영상이 도착하기 전)에 렌더러 자신의 스크롤과 같은 `STACK_VIEWPORT_SCROLL` 사건을 그 표시 요소에 보내, 칸의 장 번호("I: n (k/N)")와 스크롤 막대가 옮겨진 영상을 따라오게 한다(같은 실행·같은 stack·요청한 그 영상이고 번호가 실제로 바뀔 때만). 렌더러 자신의 순서와 같으므로, 뷰어가 이 사건에 올리는 "Loading..." 덮개는 뒤따르는 영상 도착 사건으로 내려간다.
- 일부 화면만 거절된 때 상태 줄은 표시된 화면의 말과 그 거리(`3D Cursor 표시됨 · 선택점에서 단면까지 n mm`)를 먼저 적고, 거절된 화면의 수와 첫 사유를 그 뒤에 적는다. 거리는 표시된 화면의 것이다.
- 고정 렌더러는 이미 시작한 요청을 취소하지 못한다. 그래서 모든 대기에 상한을 두고, 상한 안에 끝나지 않은 요청이 있는 화면은 **보류**로 표시해 그 화면에 새 요청(되돌리기 포함)을 보내지 않는다. 종료·취소도 상한 안에서 끝나며 확인하지 못한 되돌리기를 성공으로 적지 않는다. 되돌릴 필요가 없는 경우에도 실제 표시된 영상이 확인될 때만 복구로 적는다.
- 끝나지 않은 요청을 남긴 채 종료하면 그 창에서는 **다시 켤 수 없다**. 남은 요청이 나중에 끝나더라도 이전 실행은 화면·표식·상태를 더 이상 바꾸지 못하게 차단한다. 새로 mount해도 이미 시작된 네이티브 요청 자체가 취소되는 것은 아니므로, 확실히 정리하려면 영상 창을 다시 열어야 한다.
- 되돌리기는 **이 실행이 남긴 그 화면 그대로일 때만** 한다. 판독자가 그 화면을 직접 조작했거나 다른 프레임으로 옮겼으면 판독자의 현재 프레임을 그대로 두고 사유만 남긴다(우연히 번호가 같아도 같다). 즉 판독자의 최신 작업이 이전 프레임 복구보다 우선한다.
- 표식은 이 창에서만 유지되는 임시 표시다. 주석·측정·현재 도구·대상이 아닌 화면을 바꾸지 않으며 저장하지 않는다. 고정 OHIF의 `ReferenceCursors` 도구는 대상 화면을 먼저 이동시킨 뒤 걸러내므로 사용하지 않는다.
- **영상 창에 켜져 있다.** `config/ohif/configuration.js`의 `kinThreeDCursor: { enabled: true }`(=== true 하나만 ON, 다른 우회 경로 없음)에 따라 `config/ohif/three-d-cursor.js`가 두 모듈을 불러 도구 영역 Comparison 패널(`#kin-viewer-layout`)에 `3D Cursor` 버튼과 상태 줄을 붙인다. 모드는 판독자가 그 버튼을 눌러야 들어가고(창마다 꺼진 채 시작), 같은 버튼(`Exit 3D Cursor`)으로 나온다. 단축키는 없다. 리터럴을 `false`로 두면 모듈도 버튼도 싣지 않는다.
- 검증 범위는 `tests/three_d_cursor_model_test.cjs`(`node --test`, 순수 좌표), `tests/viewer_three_d_cursor_dom_test.py`(Playwright 격리 DOM, 고정 번들의 동작 순서를 재현한 합성 viewport), 그리고 `tests/e2e/test_three_d_cursor_accuracy.py`(dispatch 전용 CI 프로파일 `three-d-cursor-accuracy`)다. 마지막 것은 좌표를 아는 합성 CT 두 시리즈(axial·정상 oblique)와, 영상이 칸보다 작게 보이는 실제 CT 크기·간격의 512×512 세 시리즈를 실제 고정 렌더러에 적재해 실제 마우스로 클릭하고, 제품 모듈을 쓰지 않는 독립 계산과 두 가지로 대조한다.
  - **변환식끼리의 일치**(시험 01·02·05): 영상 안의 기준 표식을 canvas 버퍼에서 읽어 제품과 같은 버퍼→상자 환산으로 화면 좌표를 만든다. 제품의 변환 사슬(클릭→환자 좌표→대상 장→표식)이 그 독립 사슬과 0.3 mm·0.5 CSS px 안에서 일치하는지, 제품이 낸 점이 같은 클릭을 버퍼 단위로 물은 렌더러의 답과 같은 점인지 본다(DPR 1·1.25·1.5·2·3, resize·zoom/pan·회전/반전). 화면을 보지 않으므로 이 숫자는 화면에 대한 정확도가 아니다.
  - **화면 기준**(시험 06–09): 합성된 화면의 스크린샷에서 기준 표식과 제품이 그린 표식을 장치 픽셀로 읽는다. 실제로 누른 점(눌린 화소의 표식이 스크린샷에 보이는 자리 + 포인터의 차이)과 제품이 받은 점이 2 장치 px 이내, 제품이 그린 표식과 그 점이 대상 칸에 보이는 자리가 3 장치 px 이내(유클리드 거리)인지, 대상 칸이 보인 장이 이 측정으로 눌린 점과 구별할 수 없는 범위 안의 어떤 점에 실제로 가장 가까운 장인지 본다(DPR 1·1.25·1.5·2·3은 에뮬레이션, 1.25·1.5는 그 배율로 띄운 브라우저로도; 제품의 위치 동기를 켠 조합). 렌더러의 CPU 렌더링 경로는 열린 페이지 안에서 렌더러를 그 경로로 바꿔 본다(뷰어 설정으로 켜면 고정 뷰어가 영상을 띄우지 못하고, 제품은 그 설정을 쓰지 않는다): 제품이 낸 점이 버퍼 단위로 물은 렌더러의 답과 같아야 하고, 화면 한도는 그 경로에서 렌더러 자신의 변환이 양 축으로 영상 픽셀 반 개 치우쳐 있다는 관례를 기준으로 본다(누른 점 자체까지의 거리는 따로 적는다). 옮긴 칸에 Loading 덮개가 남지 않는지(첫 이동·이미 받은 영상·되돌리기), DPR만 바뀐 직후의 첫 클릭이 옳은 위치이거나 위 문장으로 거절되는지도 여기서 본다. 이 배치들에서 장치 픽셀 하나는 시리즈의 0.2–1.3 mm이므로 2·3 장치 px는 가장 축소된 배치에서 약 2–4 mm에 해당한다: 측정값 바로 위에 둔 공학적 한도이며 임상 정확도를 입증하는 숫자가 아니다.
  - **실기(실제 CT·판독의 사용)와 실제 Windows 125 %·150 % 모니터(GPU 합성) 확인은 하지 않았다.** CI는 headless Linux의 소프트웨어 GL이다.

세부 상태 전이와 변경 규칙은 [AGENTS.md](AGENTS.md)를 따른다. 영상 표시·주석·저장 지원은 실제 검증한 객체와 동작 범위로 구분한다. 메뉴가 보이거나 영상 요청이 성공한 사실만으로 모든 영상군의 표시·측정 정확성을 선언하지 않는다.

## DB와 인증 설정 변경

기존 Gateway 서비스 계정은 기관별 `gw-<institutionId>` 클라이언트로 구분한다. 렐름의 `gw-kin-center`는 시크릿 없는 비활성 템플릿이며, 실제 발급과 기관·역할 설정은 [Keycloak 안내](keycloak/README.md#gateway-서비스-계정)를 따른다. 이 기존 수신 계약의 유지는 기관 확장이나 운영 활성화를 뜻하지 않는다.

API 시작은 버전 관리된 migration을 `prisma migrate deploy`로 적용한다. schema 변경은 검토된 migration과 Prisma client를 함께 빌드하며, 이미 적용한 migration은 수정하지 않는다. 기존 DB의 baseline은 백업과 drift 확인 후 [baseline 도구](api/prisma/baseline.mjs)의 조건을 따른다. `AuditLog`는 추가 전용이다(트리거가 모든 역할의 UPDATE·DELETE·TRUNCATE를 42501로 거절): `AuditLog`를 바꾸는 migration은 이 가드를 어떻게 다루는지 스스로 적고 검토받는다(봉인·검증·보존 절차는 [시험 안내](tests/README.md)의 "Run C — 접속기록(AuditLog) 봉인·검증·보존").

`db push`, reset, 데이터 손실 허용이나 volume 삭제로 오류를 해결하지 않는다. 컨테이너 재생성과 realm import 파일 변경은 기존 Keycloak DB를 교체하는 절차가 아니다. 필요한 계정·realm 변경은 [Keycloak 안내](keycloak/README.md)에 따라 기존 상태를 확인하고 적용한다.

Windows bind mount에서 API 변경이 반영되지 않았다면 필요한 서비스의 재시작 후 컴파일 시각과 실행 코드를 확인한다. 전체 스택 초기화를 일반적인 문제 해결 방법으로 사용하지 않는다.

## 검증과 발행

제품 변경은 요구사항·위험·시험을 연결하고 관련 기능을 실제 스택에서 검증한다. 전달 전 개발 중에는 변경 기능과 영향을 받는 회귀, 필요한 빌드·구문 검사를 수행한다. 중간 커밋이나 턴이 끝날 때마다 69+14·전량 독립 검토·제품 태그를 반복하지 않는다.

인증·권한·판독 상태 전이·원본/저장 보존·DB/migration 변경은 해당 실패·보존 경계를 즉시 검사한다. 공유 경로 변경, 영향 범위 불명확 또는 교차 기능 실패가 있으면 아래 회귀까지 검증을 넓힌다.

의사 전달, 평가 후보 교체, 실제 배포 후보 확정 때는 **같은 최종 SHA**에서 아래 회귀를 순차 실행하고 누적 기능 통합·필요한 정확도 시험, 독립 최종 검토, 실제 CI를 완료한다.

```sh
python tests/invariants_live.py
python tests/e2e/test_worklist.py
```

시험 환경·소유 fixture 정리·기능별 추가 검증은 [tests/README.md](tests/README.md)에 있다. 시험 삭제·단언 약화·실패 생략으로 비용을 줄이지 않는다. 중간 커밋도 즉시 push해 이력을 남기되 제품 릴리스·태그와 구분한다. 현재 CI 구조와 실행 트리거는 그대로다. 문서만 바꾸면 문서 대조·링크·diff·독립 문서 검토를 수행하며 불필요한 제품 시험·재기동·태그를 만들지 않는다.

코드 발행, 사용 평가, 운영 반영은 각각 해당 조건을 확인한다. 운영 적용은 승인된 변경 범위, 기존 자료의 백업·복구 근거와 설치 조건을 갖춘 뒤 수행한다.

## 주요 경로

| 경로 | 역할 |
|---|---|
| `docker-compose.yml` | 로컬 개발 서비스와 정식 HTTPS 입구 |
| `docker-compose.prod.yml` | 운영 구성 차이; 독립적인 운영 활성화 승인을 뜻하지 않음 |
| `api/src/` | 인증·기관 권한·검사·판독·표시 저장·전송 API |
| `api/prisma/` | schema·migration·기존 DB baseline 도구 |
| `worklist-v0/hpacs-lite/` | 로그인과 판독 업무 화면 |
| `config/` · `proxy/` | 영상 서버와 같은 출처 프록시 구성 |
| `gateway/` | 기관별 영상 수신 경로 |
| `scripts/` | 데이터 입출력·백업·복원·운영 도구 |
| `tests/` | 회귀와 기능별 검증 |
