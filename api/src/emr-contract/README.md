# EMR 단위 A — 분류와 계약

이 디렉터리는 합의된 요구를 후속 구현에 전달하는 순수 계약이다. 기존 API·DB·인증·화면에는 연결하지 않는다. D589와 확인한 조문의 기록별 보존·파기 계약이며 기관은 계속 진료 사유의 1회 연장 또는 보안 강화만 할 수 있다. A의 순수 함수 검증은 후속 저장소·키 보관·API 연결의 실제 이행 완료나 모든 법령 준수 인증을 뜻하지 않는다.

|---|---|---|
| `classification.ts`, `routes.ts` | 저장 모델·API 응답·DB 밖 영상/출력의 기록 종류와 책임·보존 분류. 혼합 자료는 여러 종류로 분류 | B, E, F, L, M, N, Q |
| `lawful-defaults.ts`, `legal-basis.ts` | 완결된 제품 기본값, 강화 전용 설정, 보존·파기·키 수명 계약과 검증한 법령의 판본 | 전체 |

## 제품 기본값과 근거

`DEFAULT_CONFIGURATION`은 기록별 기간·서명 규칙을 채운 불변 객체다. `tightenConfiguration()`은 서명 추가만 허용한다. `retentionYears`·`accessYears` 설정은 같은 값·단축·연장 모두 거절한다. 알 수 없는 필드와 `undefined`/`null`도 거절하며 HospitalDecision이나 기관 결정 대기값은 없다. 실제 작성자·기관은 인증/저장 문맥에서 얻는다.

임상 후보는 **적용 보유기간 중** 수정 전 원본과 모든 판을 보존한다(의료법 제22조②). 초안을 타인에게 공개하거나 자동 서명하지 않는다. 취소·비우기·버리기는 상태 사건이며 법정 기간 전 원본 삭제 명령이 아니다. 법정 기간/허용된 연장 만료 시에는 원본도 파기한다. 제23조④ 개정 문언의 기재·추가기재·수정·열람 접속기록은 개정 시행 전에도 남긴다.

`retentionFor()`에는 **하나의 실제 기록 내용**의 종류만 전달한다. 모델/라우트의 종류 목록은 영향 조사 목록이며 전체를 개별 기록의 기간으로 전파하지 않는다. 원본·사본·서명은 원기록별 보존 단위에 결속한다. 연결된 진료기록부가 있다는 이유로 5년 소견서/영상을 10년 보유하지 않는다. `source-record`/`purpose`의 0은 독립 법정 연수 없음이며 즉시 삭제나 무기한 보유를 뜻하지 않는다. 파생 자료는 고정 원기록의 `RetentionRecord`를 사용하며 별도 타이머를 만들지 않는다.

`newRetentionRecord()`는 실제 법정 종류와 기산을 고정하고 `retentionDeadline()`이 만료를 계산한다. `startedAt`은 기록별 기산 사실로 영속화하며 마지막 열람·임상 사용·복사·재서명·연결로 재설정하지 않는다. 수정 전 원본을 포함한 법정 기록 단위의 판/서명 증거를 완전하게 묶어야 한다. 조문에는 세부 기산 산식이 없으므로 후속 저장 계층은 종류에 맞는 기산 사건을 검증·결속해야 한다. A의 날짜 계산을 조문에 명시된 기산 해석으로 주장하지 않는다.

`extendRetention()`은 **계속 진료 필요에 한해 1회**, 해당 종류의 법정 기간 범위 안에서만 만료를 연장한다(제15조① 단서). 사유·행위자·시각·새 만료를 기록하며 최초 만료 전 결정해야 한다. 짧은 연장도 1회를 소비한다. 단축·반복 연장·환자 요청만으로 연장·범용 hold·기관 연수 설정을 허용하지 않는다. 다른 법령이 실제 요구하는 별도 보존은 그 대상/기간을 확인한 새 계약이 필요하며 이 계약의 범용 옵션이 아니다.

고시 제8조① 본문은 **정보주체를 제외한 접속자**에 대해 원칙적으로 1년 이상, 제2호의 민감정보/고유식별정보 처리 시스템에는 2년 이상을 요구한다. 이 시스템의 직원/서비스 접속기록은 `accessRetention()`에서 각 `occurredAt`부터 2년으로 고정한다. 개인정보 보호법 제3조①②의 목적·최소 범위와 제21조①의 불필요 정보 파기 의무도 적용한다. 원기록의 5/10년이나 다른 접속 사건으로 기간을 늘리지 않으며 2년 이후의 구체적 별도 필요성을 일반 설정으로 대체하지 않는다. 원기록이 먼저 만료해도 접속기록의 2년 의무는 독립적으로 지키되 원문·서명 payload를 접속기록에 복제하지 않는다.

## 목적 종료·보존 전용·파기

기존 `finalize` 사건을 저장한 Finalized 판독에 **명시적 Archive와 진료 목적 종료 선언**이 더해져야 `archiveFinalizedReport()`가 보존 전용 사건을 만든다. 행위자·사유·시각·현재 공개판과 실제 finalization을 결속한다. `reportRetentionAccess()`는 사건이 없으면 정상 보존을 유지한다. 시간 경과·승인·자동 Finalized·취소만으로 목적 종료를 추정하지 않는다. Archive는 판독 본문/서명이나 만료를 바꾸지 않는 보존 수명 사건이다.

보존 전용 자료는 개인정보 보호법 제21조③에 따라 분리 저장·관리하고 일반 업무 조회에서 제외한다. 별도 보존 조회에는 목적·역할·기관 검증과 접속기록, 보존 전용 표시가 필요하다. 원본·백업에도 분리 경계를 적용하며 화면 표시만으로 이행을 주장하지 않는다. 새 Addendum/변경판에 이전 Archive를 재사용할 수 없다. 목적 종료 사건이 없어도 법정 만료 시 파기는 수행한다.

`destroyAtExpiry()`는 기본 또는 적법한 1회 연장 만료에 **지체 없이 복구 불가능한 영구 삭제**를 실행하는 계약이다(개인정보 보호법 제21조①②, 시행령 제16조①1). 정상 보존·보존 전용 모두 같다. 시행령 단서의 복원 불가능한 제58조의2 정보 처리 방법과 구별하여 이 제품은 영구 삭제를 선택한다. 내구성 있는 시작 기록 후 실행하고 성공 영수증 이후에만 완료를 기록한다. 파기 기록에는 고정 코드·단계·일자만 두며 환자/기록/판 ID, 행위자, 해시, 자유문구, 원문 오류, 요청/감사 연결 ID를 담지 않는다. 일자를 다른 로그와 결합해 개인을 복원하는 인덱스도 남기지 않는다.

B/G는 분류·기산·전체 판 집합, 원본·서명 payload·사본·복제본·복구 가능한 백업의 삭제, 연장/수정/파기 경쟁을 저장소에서 보장한다. 시작/실패만 있는 작업은 재시도하며 삭제 성공 후 완료 기록 실패·중간 중단은 실제 삭제 상태와 대조한다. 대상 정보는 제한된 실행 저장소에서만 처리하고 완료 시 제거하며 파기 원장에 영구 보유하지 않는다. A에는 스케줄러·물리 삭제·DB 연결이 없고 실제 복원 불가와 장애 복구는 후속 검증 대상이다.

## 서명 경계

제22조①·제23조①은 의료인이 진료에 관한 사항·의견을 전자의무기록으로 작성하는 경우의 서명 근거다. 모든 DB 행에 개별 전자서명이 필요하다는 조문은 아니다. 각 종류의 근거와 설명은 `classification.ts`에 빠짐없이 있다.

| 종류 | 기본 서명 동작 |
|---|---|
| 판독과 모든 수정/Addendum, 임상 Q&A, 협진, Critical Result 내용, Finding, 수동 임상 SR, 임상 비교 설명, 임상 Order | 진료 기재이므로 각 작성판에 전자서명 필요(제22조①·제23조①) |
| 개인 초안·dictation, Tech Note, 단순 ACK, 영상 전달 요청, 정정/환자 연결 사건, 분류표의 자유 문구 | 그 작업 행위 자체의 별도 서명 의무는 확인한 조문에 명시되지 않음. 작성자+서버 시각+해시를 남김. 의료인의 진료 기재/임상 사용 또는 서명된 기록의 정정이면 `signatureRequired(kind, 'clinical-entry')`가 반드시 서명을 요구 |
| 측정·Key Image·영상·썸네일·메타데이터, 외부 SR/SEG, 판독 인용/첨부·임상 문맥, 출력·PDF·복사·다운로드·제공 | 원자료와 작성자+시각+해시·원서명/출처 증거 보존. 자료 선택/형식 변환 자체에 새 서명 의무를 발명하지 않음. 이 자료로 새 진료 의견을 기록하면 해당 문서는 서명 필요. 외부 AI 원문은 재해석/재서명하지 않음 |
| 접속·전달·서명 검증·전송 근거 증거, 배정·배치·설정·양식·계정/세션·기관·시스템 운영 | 제23조①의 독립 진료 기재 서명 의무 없음. 작성자+시각+해시 및 기존 업무별 증거 계약 적용 |

`clinical-entry` 여부는 기관의 설정이 아니라 실제 기재 내용과 사용 흐름에서 서버가 정한다. 입력을 단순 작업 자료라고 표시하여 서명된 진료 기재를 우회할 수 없다. 기관은 서명을 추가로 요구할 수 있으나 필수 서명을 해제할 수 없다. 서명 의무가 없는 자료도 임상 후보에서 자동 제외하지 않으며 적용 보유기간 중 이전 판을 지우지 않는다.

## 제품이 운영하는 키

`KEY_MANAGEMENT`는 의사별 개인 키, 보호 키 볼륨, DB/키 볼륨 밖 별도 secret, 암호화 보관, 제품의 의료인 신원·서명 권한 확인을 고정한다. 개인 키를 브라우저나 감사로그로 내보내지 않는다. 복구는 신원·권한 재확인, 서로 다른 두 운영자의 승인, 암호화 백업과 분리된 secret을 요구하며 새 `kid`를 발급한다. 이전 키는 복구 후 재활성화하지 않는다. 분실·침해·퇴사 시 즉시 신규 서명을 차단하고 사유·효력 시각을 남긴다. 개인에 연결된 공개키·등록/폐기 이력은 과거 서명 검증을 위해 각 원기록의 만료까지 보존하며 독립 보유기간을 만들지 않는다. 실패 시 서명을 막되 초안과 기존 서명은 보존한다.

의료법 제23조①②·시행규칙 제16조①1·2·3·5·6은 서명 검증·이력·백업·보안·접근 방지의 근거다. 의사별 키 볼륨/분리 secret과 복구 방식은 그 보호를 수행하는 제품 기본 설계이며 법 조문이 특정 구현을 지정했다는 뜻은 아니다. 실제 키 저장소와 복구/폐기 실행은 C의 구현 대상이고 A에서는 계약과 키 상태 전이만 제공한다.

## 사건과 서명 바이트

`write`/`additional-entry`/`modify`는 기재/추가기재/수정이다. 승인·서명, amendment, Addendum, 취소, 점유 해제, 초안 저장/비우기/버리기는 각각 별도 행위다. `provide-prepared`는 서버 제공 준비이고 전송 종료·중단, 클라이언트 표시, 명시적 ACK와 같지 않다. 후속 사건은 앞 사건과 동일한 대상/판에 결속한다. `user-view`/`background-fetch`/`service-job`은 원인을 구분하며 사람의 인지를 증명하지 않는다. 출력·PDF·Copy의 클라이언트 보고는 실제 프린터·OS 저장 완료 증명이 아니다.

필수 칸은 생략할 수 없다. 인증 실패 등으로 확인할 수 없는 신원/환자는 `unresolved`와 원인을 기록한다. 실제로 해당하지 않는 칸은 사유 있는 `not-applicable`로 구분한다. 성공 제공의 대상은 그때 반환한 집합이며 나중에 검색해 재구성하지 않는다. 빈 목록은 빈 대상 집합을 명시한다. G는 신뢰 프록시에서만 IP를 취하고 B는 append-only 저장과 독립 실패 저널을 구현해야 한다. 감사 연결 ID는 독립 난수 `audit:<UUID>`이며 인증 계층이 세션·토큰으로 받아서는 안 된다. 순수 검증만으로 DB 내구성·프록시 신뢰·인증 거절을 입증하지 않는다.

서명 v1은 `SignaturePayload`의 필드를 `canonicalPayload()`에 적힌 순서로 직렬화한 JSON UTF-8 바이트다. 중첩 객체도 고정 순서이고 배열은 입력 순서, 빈 문자열과 `null`은 명시적으로 유지한다. BOM·끝 줄바꿈·JSON 장식 공백을 넣지 않는다. **본문의 공백·CR/LF·Unicode 조합 형태는 변환하지 않는다.** NFD와 NFC는 다른 원문으로 서명하며 홀로 있는 surrogate, 알 수 없는 필드/형식은 거절한다. 형식을 바꿀 때 버전을 올린다. 이전 판과 첨부는 기록/판 ID와 SHA-256을 함께 고정한다.

JWS는 `{protected,payload,signature}` 형식의 unpadded base64url이며 보호 헤더는 `alg`, `kid`, `typ` 순서, 값은 ES256·등록 키 ID·`emr-signature+jws`이다. 서명값은 64바이트 R||S다. `inspectSignatureEnvelope()`는 구조만 검사한다. C는 기존 암호 도구로 내용 무결성, 제품이 확인·등록한 신원, 서명 당시 키의 소유/활성 상태를 각각 검증하고 침해 의심 기간을 별도 표시해야 한다. 현재 DB 머리에서 payload를 재조립하거나 나중의 키 폐기만으로 이전 서명을 지우지 않는다.

## 판독 상태와 검증 범위

첫 입력→In Progress, Save→개인 중간 저장, 다른 판독의의 Release→Unread와 점유 세대 증가다. Release는 모든 개인 초안을 보존한다. 세대가 오래된 저장·갱신은 거절한다. Approve는 즉시 공개하고 `firstApprovedAt`·`originalSignerId`·`amendUntil`을 함께 고정한다. 24시간 직전까지만 원서명자의 새 서명판 amendment를 허용하며 정확히 기한에 도달하면 거절한다. 다른 작성자의 Addendum은 별도 불변 참조로 유지된다.

Finalized는 공개판을 유지한다. 처리 지연이 있어도 효력 시각은 `amendUntil`이며 기한을 늘리지 않는다. 사유 있는 취소는 Cancelled와 취소 사건으로 남고 기존 공개판 참조·본문·Addendum·시계를 보존한다. 이 참조는 이력용이며 소비자는 Cancelled를 정상 유효 판독으로 표시해서는 안 된다. Reset 명령·재승인·Unread 복귀는 허용하지 않는다. P의 지정 상급자 승인·자기 승인 금지와 Defer 사유도 계약에 포함한다. 순수 함수의 역할/기관/서명 권한 입력은 G가 검증한 문맥이어야 한다. I는 제출한 이전 판, 새 판 ID의 전체 이력상 유일성, 서명 검증, 상태·공개·감사의 원자성을 DB에서 확인한다. 개인 초안 revision과 점유 세대, 확정판 경쟁 조건은 별개다.

REQ-EMR-01/17/19 → RISK-EMR-01/17/19 → TEST-EMR-01/17/19-A는 분류 누락·법정 기간·1회 연장·보안 강화·명시적 보존 전용·개인정보 없는 파기 기록·키 경계를 검사한다. REQ-EMR-04/05 → RISK-EMR-04/05 → TEST-EMR-04/05-A는 바이트 결속·봉투를 검사한다. REQ-EMR-06/07 → RISK-EMR-06/07 → TEST-EMR-06/07-A는 사건 필드·내구성 선후를 검사한다. REQ-EMR-02/12/13 → RISK-EMR-02/12/13 → TEST-EMR-02/12/13-A는 점유·역할·기한·취소를 검사한다. REQ-EMR-20의 실제 최종 CI·G3·독립 판정·법령 재대조·제품 운영 증거는 R에 남는다.

시험 `tests/emr_contract_test.cjs`는 설치된 Prisma의 generator 프로토콜로 현재 schema의 DMMF를 받고 TypeScript AST로 전체 API 라우트를 수집한다. 새 모델·라우트를 기존 분류에 자동 편입하지 않는다. 프록시·브라우저 제공면은 별도 명시 목록이며 N/O에서 실제 제공·인가·실패 시험으로 결속한다. 암호 서명, 실제 DB/네트워크, 운영 보존, 의사 확인은 이 순수 시험의 범위 밖이다.

`routes.ts`의 `ROUTE_CONTRACTS`는 각 정확한 경로에 기록 종류, 업무 행위(`read`/`write`/`export`/`auth`), 호출 원인 종류를 명시한다. `ROUTE_CLASSIFICATION`은 기록 종류만 필요한 소비자를 위한 같은 목록의 투영이다. 호출 원인 목록은 가능한 호출 문맥이며 실제 사건의 원인을 선택하는 기본값이 아니다. 후속 구현은 사용자 동작·백그라운드 요청·서비스 작업 중 실제 원인을 결속해야 한다. DICOM 인가의 204는 영상 제공 증거가 아니고, 출력 미리보기는 출력 완료 증거가 아니다. 경로 판독은 문자열 패턴 대신 TypeScript가 해석한 실제 Nest 데코레이터 export 심볼을 대조한다.
